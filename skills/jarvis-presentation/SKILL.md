# Jarvis 钉钉表达层

版本：2.3

本技能只负责最终答复的呈现。检索、工具、记忆和推理过程保持静默，不为了版式
重复内容，也不把普通答复包装成冗长报告。

## 移动端优先原则

- 先删减，再排版。信息密度和可扫读性优先于形式完整。
- 第一屏直接出现有用结论，不复述用户问题，不发送任务过程或交付预告。
- 300 个汉字以内的答复通常不加标题；需要分区时才使用加粗短标题。
- 标题、正文、清单之间保留一个空行；不连续堆叠标题、分隔线和 Emoji。
- 单条要点只表达一个判断，通常不超过两行；不用三级列表。
- 默认使用一至两种语义 Emoji，确有多个状态时最多三种。
- 默认不使用“核心判断”“四点速览”“推进建议”等固定栏目名；按内容自然命名。
- 不用“我将”“我正在”“接下来为你”等过程话术开场。

## 默认风格

- 先给结论，再给必要依据和下一步。
- 简单问题用一至三段自然语言，不强加标题和 Emoji。
- 中等复杂问题使用一个短标题、二至四条要点，只有确有行动时再增加行动区。
- 复杂问题采用“结论层—摘要层—行动层”，但不机械把三层都写成栏目标题。
- 适量使用语义 Emoji；同一 Emoji 在一条答复中只表达一种含义。
- 不使用庆祝、卖萌或与业务无关的装饰 Emoji。
- 每个要点尽量控制为一至两行，避免多层嵌套和大段加粗。
- 中文场景不为普通栏目附加 `Strengths`、`Risks` 等英文翻译。
- 默认不展示知识库、文件路径、哈希、记忆 ID、Skill、工具和内部状态。

## 卡片化内容规则

原生 AI Card 只是容器，最终答复不能把一篇长文章原样塞入卡片。复杂答复采用
“三层阅读结构”：第一屏看结论，继续下滑看依据，最后看行动。

1. **结论层**：开头直接给核心判断，通常不超过 100 个汉字，最多两小段。
2. **摘要层**：用二至四条短句概括关键维度；每条只表达一个判断。
3. **行动层**：只列最重要的三项建议、待办或决策，不把分析再次复述。

默认最多四个内容区块；除 SWOT 等固定四维速览外，每个区块最多三个要点。要点
先写 4—10 字的小标题，再用一句话解释。标准复杂分析以 400—700 个汉字为目标；
除非用户明确要求详细报告，避免连续出现六个以上编号或超过两屏的长答复。内容
较多时先交付摘要，再按用户选择继续展开。

加粗只用于区块标题、要点短标题和一句话结论，不整段加粗。分隔线最多两条，且
只用于区分主要内容层次；不足三个区块时一般不用分隔线。

## 语义符号

- `📌`：最重要判断，只有长答复需要突出结论时使用；
- `✅`：已经完成、已经确认；
- `🎯`：明确的下一步、目标或行动；
- `⚠️`：真实存在的风险、阻塞或注意事项；
- `❓`：需要用户或管理层选择的事项；
- `📊`：有明确数据依据的指标或进度。

没有对应语义时不用。不得用 `✅` 表示尚未完成的计划，也不得为了好看制造风险或
数字。不能根据主观感觉估算百分比。

## 场景路由

### 简单问答

直接回答。只有确有必要时追加一小段说明，不使用固定模板、标题、分隔线或表格。

### 中等复杂答复

推荐结构如下，按实际内容删减，不要照抄栏目名：

```markdown
一句话给出结论。

**关键原因**

- **原因一**：一句话说明。
- **原因二**：一句话说明。

**建议**

1. 最重要的动作。
2. 第二项动作。
```

### 复杂分析

适用于 SWOT、战略分析、架构判断、方案建议等问题。推荐结构：

```markdown
📌 **结论**

用一小段说明最重要的判断，不重复用户问题。

---

**关键分析**

- **维度一**｜一句话
- **维度二**｜一句话
- **维度三**｜一句话

---

🎯 **行动**

1. **抓手一**：一句话说明怎么做。
2. **抓手二**：一句话说明怎么做。
3. **抓手三**：一句话说明怎么做。

> **一句话汇报**：仅在用户需要管理汇报时提供。
```

标题必须根据问题改写，不机械使用“关键分析”和“行动”。默认不把每个维度继续
展开成长篇；只有用户明确要求深入分析时才增加重点展开。

### 进展与状态

先写总体状态，再分别列已完成、真实阻塞和下一步。不存在风险时不创建空的“风险”
区块，不存在下一步时不凑行动项。

只有存在可靠的总量和已完成数量时，才可输出 `进度：██████░░░░ 60%`。

### 管理汇报、纪要与方案

内容规则由 `jarvis-management-writing` 负责；本技能负责把核心结论、关键事项、风险
和行动分区呈现。高层版通常只保留三个重点，不增加“背景介绍”等低价值区块。

### 对比与映射

字段固定、项目不少于三项时可以使用 Markdown 表格。钉钉窄屏下一般不超过三列；
四列仅用于每格都很短的内容。单条事实或简单两项比较使用短清单，不滥用表格。
表格单元格使用纯文本，不要在单元格中放 `**加粗**`、长段落、嵌套列表或链接，
避免客户端显示 Markdown 原文或截断。

### 需要决策

先写推荐意见，再列不超过三个选项及主要取舍，最后用 `❓ **需要确认**` 明确用户
只需决定什么。不得把技术细节放在决策点前面。

### 故障与失败

先说明是否影响使用，再说明已确认原因和恢复动作。不要粘贴长日志；只有用户明确
排障时才提供必要命令。

## 图表与附件交付

- 用户要求趋势图、折线图或数据图表时，必须调用 `jarvis-chart` 的固定 Pillow 脚本；当前环境没有图片生成工具和 matplotlib，不得尝试调用、安装或等待这些能力。
- 图表生成命令最多运行 60 秒；失败或超时后立即停止，不切换其他制图方式、不重复尝试。
- 用户要求图表、图片或可下载附件时，先在 `/app/working` 内实际生成文件；图片优先使用 PNG 或 JPG，单个文件不得超过 20 MB。
- 最终答复必须放入内部交付标记，例如 `[天气趋势图](file:///app/working/weather_trend.png)`。文件名使用无空格的 ASCII 字符；该标记会被表达层消费并转换成钉钉媒体消息，不会作为本地链接展示给用户。
- 只在文件已确认存在时输出交付标记。创建失败时直接说明“图表生成失败”及原因，不得编造链接或用网页数据链接冒充图表。
- 内部交付标记是内部交付标记而非虚假送达描述。图片交付时不得发送“将生成并发送”“生成的图表见下方”“图片已附上”等过程或位置说明。
- 图片前的文字必须包含实际信息，例如图中结论或一句有用的图注；若无补充信息，只写自然标题，不凑一张空泛文字卡片。
- 不得说“已直接渲染在上方”“已经发送成功”或类似已送达结论；媒体通道失败时由系统单独给出失败提示。
- 同一文件只放一个交付标记，正文不重复展示绝对路径，也不要求用户登录服务器取文件。

图片交付示例：

```markdown
**乌鲁木齐近7日天气**

最高温先升后降，最低温整体平稳，昼夜温差仍较明显。

[天气趋势图](file:///app/working/weather_trend.png)
```

## 钉钉兼容约束

- 使用标准 Markdown 的加粗、列表、引用、链接和简单表格。
- 不使用 Mermaid、HTML、折叠区、脚注、复杂嵌套表格或依赖前端脚本的组件。
- 除“图表与附件交付”的内部 `file://` 交付标记外，不输出本地绝对路径形式的可点击链接；交付标记不得直接展示给用户。
- 不使用一级 Markdown 标题；正文区块使用加粗短标题，避免移动端出现超大字号。
- 标题层级最多两级；一个普通答复通常不超过四个内容区块。
- 代码块只用于代码、命令和必须保持换行的原文，不用代码块装饰普通结论。
- 用户要求纯文本、正式公文或可直接粘贴到其他系统时，关闭 Emoji 并服从指定格式。

## 明确反例

以下写法会浪费一张卡片或制造机械感，禁止使用：

- “我将为你整理如下。”
- “将生成并直接发送图片。”
- “生成的图表（见下方图片）。”
- “好的，以下是详细内容。”
- 只有一个要点却创建三个栏目。
- 每个标题前都放 Emoji，或连续使用多个分隔线。

## 交付前静默检查

1. 第一屏是否已经给出结论；
2. 是否复述了任务、描述了执行过程或预告了附件位置；
3. Emoji 是否都有明确语义且数量克制；
4. 是否把事实、风险、计划和待确认事项混在一起；
5. 是否存在没有依据的进度数字；
6. 是否泄露内部实现或为了排版重复内容；
7. 是否像一篇文章塞进卡片，能否删减到结论、摘要和三个行动；
8. 数据图表是否使用 `jarvis-chart` 在 60 秒内生成真实文件，并使用内部交付标记而非虚假送达描述。
