# 钉钉表达层 V2

## 目标

表达层 V2（当前规则版本 2.4）通过“结论—摘要—行动”控制内容密度，让用户先
看到核心判断。这套规则同时适用于原生 AI Card 和最终 Markdown 消息。

当前默认关闭流式输出，V3 收尾补丁让非流式对话绕过预创建 AI Card，使用最终
Markdown 消息，避免卡片停留在“处理中”。启用脚本保存的 `message_type=card`
和模板 ID 只是配置；实际对话路径以 `dingtalk_inbound_delivery` 为准。原生卡片
的最终答复方案仍需真实接口及客户端验收，不能仅凭配置或容器健康认定已生效。

## 默认卡片结构

1. 开头直接回答用户问题：通常不超过 100 个汉字，最多两小段；
2. 二至四项必要依据：每项一个判断，短标题加一句解释；
3. 有行动需求时列一至三项动作；没有则省略；
4. 只有用户需要管理汇报时增加一句话汇报结论。

普通回答最多四个区块，每个区块最多三个要点。详细报告、正式公文和用户指定格式
不受默认长度限制，但仍应先给结论。默认复杂分析约 250—450 个汉字，必要时
可写 400—700 字，不为字数凑背景。简单问题用一至三段，不强加栏目或 Emoji。
完整规则以 `skills/jarvis-presentation/SKILL.md` 为准。

## 模板视觉建议

在钉钉卡片模板编辑器中保留现有 `content` Markdown 变量，并在变量上方增加一个
静态标题区：

- 标题：`JARVIS · 智能分析`
- 背景：浅橙色 `#FFF3E8`；
- 主文字：深灰色；
- 强调色：平安橙 `#F05A23`；
- 正文：白底，不增加外层边框和重复标题；
- 页脚：可选用浅灰小字 `重要决策请结合业务实际复核`。

静态标题由模板负责，模型正文不再重复“Jarvis 分析”“Codex 回复”或任务编号。

## 部署

代码更新后执行：

```bash
chmod +x scripts/*.sh
./scripts/backup.sh
docker compose build jarvis
docker compose up -d --force-recreate jarvis
# 确认容器 healthy 后再执行：
./scripts/upgrade-presentation-v2.sh
```

脚本会先备份，再安装新版 Skill、安全策略并重启，最后验证
`presentation_version=2`、Codex final-only、AI Card 配置和容器健康状态。还需检查
`dingtalk_inbound_delivery` 并在新会话中实测；该脚本不会修改钉钉平台的视觉模板，
也不会重新构建镜像；上面的 build 步骤将新版表达规则和补丁一起打包。
若构建或健康检查失败，停止后续步骤并按服务器的备份恢复流程处理。

## 人工验收问题

```text
分析一下平安开展线上经营的优势、劣势、机会和风险，并给出推进建议。
```

通过标准：第一屏出现核心判断；正文不使用英文栏目名；默认不把 SWOT 四部分全部
展开成长文；建议不超过三项；不展示 Thinking、工具调用或知识库路径。

补充验收：

- 问“今天任务完成了吗”：直接说明已完成、未完成或尚无法确认，不强加分析模板。
- 问“比较两个推进方案”：先推荐，再给各方案的优势、代价和适用条件，窄屏不出现长表格。
- 问“详细列出四个维度及建议”：完整回答四个维度，不能为了缩短而漏掉用户要求。
- 长答复仍正确渲染加粗，超过消息长度限制时分段发送，不显示字面的 `**` 或 `\\n`。
- 最终答复结束后无残留等待动画；图片和附件独立交付，失败时给出明确提示。

### 预期回答示例

问题：项目进展怎么样，下一步做什么？（假设已核实以下事实）

```markdown
试点已完成，暂未具备全面推广条件；先解决登录兼容问题，再扩大范围。

**当前进展**

- **已完成**：两个试点部门通过核心流程验收。
- **待解决**：旧版客户端登录失败，影响后续推广。

**下一步**

1. 修复旧版客户端登录问题，以原失败用例复测通过为完成标准。
2. 复测通过后扩大试点，记录实际使用问题，再决定推广范围。
```

示例中的部门数量和故障仅用于展示排版，实际回答必须以已核实的信息为依据。
